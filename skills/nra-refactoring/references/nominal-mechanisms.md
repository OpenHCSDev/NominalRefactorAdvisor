# Choosing a nominal mechanism from the domain obligation

These are **candidate mechanisms and ways to break them**, not a pattern→rewrite table. The user supplied string-status, dict-bag, flag-avalanche, god-manager, exception-routing, autoregistering-value, explicit-state and MRO-mixin examples to show the *direction* they want. The agent has to run the [owner-finding procedure](finding-owners.md), name the answers the task requires, and pick only the mechanism that actually represents them. Don't make the user do that trace, and don't treat the illustrative snippets as proven fixes.

| Source lead | Candidate owned structure | What must be true / negative control |
|---|---|---|
| Raw status strings and repeated `if status == ...` | For states that carry behavior, prefer a **public state ABC** with substitutable case classes that own their data, invariants and transitions, and inherit the common algorithms. Use an **Enum** when it has its own value-only or boundary-vocabulary role, not just because the family is small. Consumers call the public behavior contract instead of re-reading tags. | Keep legal/illegal transitions, order, unknown persisted strings and wire spellings. An ordinary method on the Enum **class** is shared by every member, so hiding `if self is Status.PENDING` inside it is still a switch. `Enum` + handwritten `ALLOWED_STATES` + leftover switches is a mirror, not polymorphism. A list of allowed next classes can itself be an independently writable transition graph: hang each edge on a declared owner, or derive it if another relation determines it. Don't add a subclass just because a string showed up. |
| Nested `payload["address"]["country"]`, scattered shape guards | Use an explicit decoder/factory, or a constructor/`__post_init__` you write, to parse and validate a **domain value object/dataclass** at the external boundary. Domain behavior stays on the object and serialization stays an adapter. If variants have different public obligations, add a real ABC and children. | A local dict or an external wire schema can be fine. Don't push Textual/UI/JSON code into a domain object, and don't invent 50 validation subclasses when one value object does it. A generated dataclass `__init__` doesn't validate annotation types, nested payloads or domain invariants. Keep missing/malformed/unknown field behavior and construction effects, and test the validation boundary you actually have. |
| Boolean avalanche (`is_admin`, `send_email`, `skip_validation`) | If stable, named operations really have different contracts, use separate command classes/functions. If **independent nominal capabilities** combine, cooperative mixins under an ABC can derive the combinations through Python C3. The shared algorithm goes upstream and leaves only the hooks that can't be shared. | Flags can be legitimate runtime options, and class-per-combination can blow up the domain. Verify allowed combinations, call sites, defaults, decorator/constructor effects, `super()` participation, MRO, side-effect order, exception paths and notification timing. MI composes things. It doesn't replace every flag or priority check. |
| Giant manager storing model, UI, history and billing | Give state and transitions that live independently their own owner. Views and adapters derive what they show from it (#58 is a retrospective example). | Pulling out pass-through `*Service` wrappers can leave the manager's writable facts exactly where they were. Prove identity/lifecycle across separate caller producers, nested state, callbacks, descriptors and saved/live phases before you claim one runtime owner. |
| `except DomainError` routes an expected business result | If consumers need a normal, closed set of outcomes, a result variant can own that answer. Keep exceptions for boundary failures that really are exceptional. | Don't rewrite just because creating an exception costs something. Check transaction rollback, stack/provenance, caller catch order, subclassed exceptions and API compatibility. A `Result` plus parallel exception dispatch just adds a second carrier. |

## ABC, MI, metaclass: pick the narrowest tool that's justified

- **ABC polymorphism:** Use it when consumers need one named public contract and the cases behave meaningfully differently but are substitutable. Common validation/template logic goes on the parent. Children get only the hooks that vary. A subclass set or `__subclasses__()` census is not automatically closed or stable across imports. Verify every required `(implementation, consumer/class)` pair, including the missing and forbidden distinctions, before claiming coverage. Generic consumers call the parent contract. Serialization or UI stays a separate adapter where that fits.
- **Multiple inheritance:** Use it only when two independently meaningful capabilities have to combine on the same object and native C3 lookup gives the precedence you want. Check method resolution, `super()` chains, cooperative constructors, overlapping attributes/slots, decorators and required behavior across all the descendants. The order `ValidationMixin, NotificationMixin, BaseCommand` is observable policy. It is not a syntactic trick for deleting three booleans. If two capabilities aren't truly independent, put the shared implementation in one parent.
- **Metaclass/registration:** Use it when the *class declaration itself* has to enforce a contract or register a discoverable family at class-creation time. Registry entries should be **derived from the declared identity**, with collision/alias/abstract-class rules owned right there. Consumers shouldn't keep a second handwritten roster. Check `ABCMeta` compatibility, inherited registration keys, C3/metaclass conflict, class-body/decorator execution, dynamic imports, mutation and unknown-name behavior. A metaclass that makes up keys with `name.lower().replace("value", "")`, uses `hasattr` to guess inherited registry state, or silently ignores unknown payload keys brings back the same stringly mess it was supposed to fix. #60 already had `AutoRegisterMeta` elsewhere before the independent family/policy specs were removed. Metaclasses don't solve mirror ownership on their own.

## What the epoch-defining PR sources actually teach

These are **primary Git before/after source** contrasts. They aren't endorsements of the PR titles or proofs of equivalence. Re-read the stated revisions before you copy a mechanism. The exceptions the PR kept are often the real lesson.

- **#38 memory conversion, merge `05eb87f07` `^1→^2`:** Before, `core/memory/converters.py` already validated types from `MemoryType` but used repeated source/target branches and accepted `allow_cpu_roundtrip`. After, `MemoryType` gets a converter property and `to_X` methods are attached **dynamically at import time**. A `MemoryTypeConverter` ABC declares four hooks. `conversion_helpers.py` still has an Enum-keyed `_OPS` table of expression strings run through `eval`. `CPU_MEMORY_TYPES`/`GPU_MEMORY_TYPES` are authored classifications, while `SUPPORTED_MEMORY_TYPES`/`VALID_MEMORY_TYPES` derive from those and the Enum. The broad DLPack exception→CPU fallback and the missing `allow_cpu_roundtrip` argument are parity questions. **Lesson:** Enum + ABC + generated methods can squash a cross-product, but that doesn't give you static membership or one-edit extension. Tell authored policy facts apart from derived sets, and test both a new memory type and the failure behavior.
- **#44 widget capability, merge `05d1a32f` `^1→^2`:** The child `ValueGettable`/`ValueSettable` ABCs and `WidgetDispatcher` are a real capability boundary for get/set. A combined Qt/ABC metaclass supports manager declarations. But `WidgetService.clear_widget_to_default_state` still switches on Qt types and changes the final fallback from guarded `hasattr(clear)` to unguarded `clear()`. `WidgetMeta` registration warns and **overwrites** duplicate widget IDs, despite its docs saying it fails loudly. **Lesson:** ABC polymorphism can be right for one operation while a UI adapter keeps another dispatch. Read metaclass collision policy from what executes, not from docstrings.
- **#58 state, PR-branch step `43a6cba5b`:** `ObjectState` stores parameters, defaults, nested states, user-set/reset fields and saved baselines. PFM later forwards five direct properties. A sixth uses dynamic `getattr`. Callers separately create/look up states, and nested managers pass a distinct nested state. **Lesson:** state extraction can remove model storage from the UI, but a shared field name or a lifecycle docstring doesn't prove every path shares one object.
- **#60 CellProfiler, direct step `5a57218b3→63f0ede15`:** `CellProfilerModule(ABC, metaclass=AutoRegisterMeta)` owns module name, aliases, settings and hooks. `__init_subclass__` validates declarations and duplicate names. `ScopedMeasurementModule(ImageMeasurementInputModule, ObjectMeasurementInputModule)` composes two cooperative `measurement_artifact_inputs` implementations through C3. Semantics derive from backend registration **and separately** `SetupModuleCompiler`. Unknown names and selected trait projections stay separate checks. **Lesson:** MI can express overlapping capabilities instead of a giant switch, but the actual MRO output order, registry discovery, aliases and setup/unknown behavior are obligations you still have to check.
- **#69 materialization, merge `b5abe6aa6` `^1→^2`:** Old `MaterializationSpec(handler: str, options: dict)` picked a registered string handler. New frozen `CsvOptions`/`JsonOptions` compose `FileOutputOptions`, `SourceOptions`, `TabularExtractionOptions` by MI. `MaterializationSpec` rejects raw dicts and unregistered option types, and `materialize` dispatches by `type(opt)`. `_WRITERS_BY_OPTIONS` is still filled by **explicit** `register_single_file_writer`/`@writer_for` calls carrying a separate `MaterializationFormat`. A naming convention does not discover them automatically, whatever the PR prose says. **Lesson:** typed data and type-keyed dispatch are real wins. Still, test a new output type across option declaration, writer registration and format label before you claim a single determining owner.

**Naming is not ownership.** A new `FooAuthority`/`FooDeclaration` wrapper that just forwards facts is a pointless layer. Prefer the domain name (`OrderState`, `Address`, `CellProfilerModule`, `ObjectState`) and show which formerly independent answer or operation it now determines. Likewise, not every raw list in logic is wrong. A derived local `choices_set`, or a UI subset that's deliberately independent, isn't a manual copy of the whole domain.

**Finish by trying to break it:** add one new case/field/capability, change an alias, and feed an unknown external value. List every authored edit needed before and after. If a second roster, a caller-side switch or a fallback still has to be kept in sync by hand, your polymorphism/metaclass/MI hasn't delivered the maintenance win you claimed. Then use NRA's existing staged DSL and the separate native/behavior proof gates. No illustrative design proves equivalence.
